## CodeQL

Disabled in `tools.json` (`enabled: false` is the only switch), and the manifest parser rejects an enabled CodeQL entry. It is blocked on the licensing decision (P0-10) and has no image reference, so the argv builder refuses it regardless. `codeql/Dockerfile` is a stub that cannot build without an explicit bundle URL and checksum. Nothing here pulls, builds or runs CodeQL.

## How each tool is run

All runs are `--network none` in the jail, source mounted read-only at `/src`, results written to the mounted `/out`. Argv is an array for `ToolRunnerPort.run(image, args, mounts)`; no shell strings, and nothing from inside the scanned repo reaches argv.

- Semgrep: only our own rules, mounted at `/rules` (`--config /rules`). Never `--config auto` or registry packs, so a `.semgrep.yml` or `.semgrep/` planted in the repo is never read (a docker test checks this). `--metrics=off`, version check off. Hardened with `--no-git-ignore` (never runs git in the repo, so a hostile `.git/config` cannot execute anything), `--disable-nosem` and `--x-ignore-semgrepignore-files`. `--max-target-bytes=0` removes the silent 1 MB cap. Semgrep's own per-file timeouts stay at their defaults, so a single hostile file cannot stall a run. A file that times out or fails to parse is reported by Semgrep as a SARIF notification while the exit code is still 0; `runTool` surfaces these as `partial: true` with the notifications attached. A very large file is therefore either scanned or reported, never silently dropped. SARIF to `/out/semgrep.sarif`.
- OSV-Scanner: `scan source --offline` against a vendored database mounted read-only at `/tmp/osv-scalibr` (`<dir>/<ecosystem>/all.zip`). `--config` is always our empty `config/osv-scanner.toml`, and `--no-ignore` scans lockfiles a repo `.gitignore` would hide. `--no-call-analysis=all` because call analysis runs the Go toolchain (govulncheck) and Rust build scripts on repo content, and can mark findings "uncalled"; reachability is decided elsewhere. Exit 1 means vulnerabilities were found. Exit 128 means no packages were found and no report is written; `runTool` treats it as an empty result only if discovery's own check finds no lockfile OSV-Scanner could read (`findOsvLockfiles`), and throws `ToolFailedError` otherwise, because a malformed lockfile also exits 128. OSV-Scanner prints extraction errors only to stderr, and `ToolRunnerPort` does not return stderr, so the reason is lost; returning stderr (or a log path) from the port is a question for the lead. OSV-Scanner also exits 1 with a report when it parsed one lockfile and dropped a malformed one, so `--all-packages` makes every parsed lockfile appear as a source, and `runTool` marks the run `partial` for each lockfile the snapshot has (per `findOsvLockfiles`) that is missing from the report. The lockfile name list was derived by probing the pinned 2.7.0 image with each candidate name (garbage content, one file per directory) and keeping every name it reacted to, plus names found in the binary that did not react to garbage (they may need valid content, or a specific directory such as `node_modules/.package-lock.json` or `gradle/`). It is deliberately over-inclusive: an extra name only turns an empty result into a failure or a partial one. Output is OSV JSON (`--format json`, what the L1-03 normalizer reads) at `/out/osv-scanner.json`.
- gitleaks: `dir /src` with our mandatory `config/gitleaks.toml` (`--config` is always set so a repo `.gitleaks.toml` is never loaded), `--ignore-gitleaks-allow`, `--redact`, `--exit-code 0`, and `--max-archive-depth 3`, which lets it search inside archives it can unpack (works offline). That is a partial help only: a member stored as UTF-16 or behind another skipped header is skipped again, and a truncated or nested archive may not unpack. SARIF to `/out/gitleaks.sarif`. Coverage is the hard part, see below.

### gitleaks coverage

gitleaks exits 0 whatever it skipped, so `runTool` works it out on the host. What gitleaks does, probed on the pinned image with a recognised header followed by a plaintext secret: it skips the "application" file types (PDF, PostScript, RTF, zip and every other archive format, Windows and Mach-O executables, Java classes, SQLite, Chrome extensions, NES ROMs, Word documents, DICOM, Flash, cab) and reads images, audio and video as text. Fonts are skipped too: with complete headers gitleaks logs "skipping binary file" with mime type `application/font-sfnt` or `application/font-woff` (a docker test covers .woff, .woff2, .ttf and .otf). Media types were probed with complete headers and debug logging, not just magic bytes. Its library also checks lengths and structure beyond the magic bytes, so a type read in the probe with only its magic may be skipped when the header is complete; discovery therefore treats every type outside the media groups as skipped. It also reads text in chunks of about 100 KB, extending a chunk up to 25 KB to find a blank line and otherwise cutting near 125,000 bytes, so a secret across that cut is missed.

Discovery cannot import that library, and a header allowlist always lags it, so `runTool` streams every file once on the host (bounded memory, a few files at a time, stopping early once a file is decided) and over-flags. Everything below except `binary-media` is a coverage loss: a notification, never truncated, listed by severity, and it makes the run `partial`:

- `binary-header-mismatch`: a skipped-type signature on a file whose extension does not agree (`%PDF` in a `.txt`). This is the hiding technique.
- `non-text-content`: control characters at the start, or NUL bytes or invalid UTF-8 anywhere in the whole file (UTF-16 text, or a UTF-16 secret appended after plain text). The first 100 KB (gitleaks' first chunk) is checked for signatures; the whole file for NUL and UTF-8.
- `unreadable`: the host user could not open the file. This is judged by the uid discovery runs as, so it is unreliable if the worker runs as root (root can open mode 000 files that the unprivileged jail cannot).
- `skipped-file-type`: a skipped type with a matching extension (zip, jar, gz, pdf, sqlite, exe, ...). Archives always count: gitleaks unpacks some, but discovery does not unpack them to inspect members, so a UTF-16 member, a member behind another skipped header, a nested or a truncated archive is a silent loss. Unpacking on the host with a depth cap would close this, but is not done.
- `archive-name-mismatch`: a file whose name gitleaks reads as an archive (`a.gz`, `a.zip.js`, `config.zip.env`, see the windows pass below) but whose content carries no archive signature. gitleaks drops it with exit 0. It is scanned in a window under a neutral name, and is still flagged.
- `chunk-split-risk`: a text file over 100 KB with a 25 KB stretch that has no blank line. A blank line is an empty line or one holding only spaces, tabs or carriage returns. gitleaks reads 100,000-byte chunks and looks up to 25,000 bytes further for a blank line to cut at; if there is none, the cut is at a hard limit, and every possible hard cut lies inside such a stretch. A whitespace-only line restarts the stretch AT that line (its own bytes count), because gitleaks only cuts early at a blank line whose newlines both come after the 100,000-byte point, so a whitespace-only line straddling that point does not help (a docker test reproduces the miss). gitleaks also repeats its binary check on each chunk until it has seen a newline, which the same stretch covers. Since the windows pass below covers anything up to 16,000 bytes, this flag now stands for secrets longer than the overlap; it is kept as defence in depth.
- `multiline-split-risk`: a file over 100,000 bytes with a private-key block that has a blank-ish line (`\n[ \t\r]*\n`) inside it. The block is matched like gitleaks' private-key rule: begin `-----BEGIN[ A-Z0-9_-]{0,100}PRIVATE KEY( BLOCK)?-----` including its trailing dashes, close `KEY( BLOCK)?-----` (both case-insensitive), with at least 64 characters between the end of the header (after its dashes) and the close, as gitleaks requires, measured from the first header of the block. A second begin marker while a block is open (a decoy comment, a stray marker, a doubled header) does not close or reset the block, and a close marker too near the header (an `xKEY-----` line) is ignored, because gitleaks reads on past both. Constant-size state. Kept as defence in depth behind the windows pass: it flags keys that no cut would split, and keys longer than the overlap.

`binary-media` (an image, audio or video signature on a file whose extension agrees) is informational: gitleaks reads these, so a plaintext secret inside is found (a docker test shows it). They are returned as `binaryMediaFiles` and do not make the run partial. The same signature on a file with another extension (`GIF89a` at the top of `app.env`, `ID3` in a `.js` or `.txt`) is a `binary-header-mismatch`, a coverage loss, and the text checks still run. For real media files the text and chunk checks are NOT run (a real image has NUL bytes, so the text check would flag every one), so a UTF-16 secret, or one across a chunk cut, inside a real media file is an accepted gap.

**Windows pass (how chunk cuts are handled).** Modelling gitleaks' cuts was a source of repeated misses, so `runTool` no longer relies on it. For every plain text file over 100,000 bytes (exactly 100,000 is not windowed, 100,001 is; a unit test pins this), and for every plain text file whose name gitleaks reads as an archive (see below), the host writes overlapping windows, each under 100,000 bytes (90,000 plus a 19 byte neutral first line), into a directory beside the copy and runs gitleaks on that directory too. gitleaks reads a file under 100,000 bytes in one piece, so a window has no cut. Consecutive windows overlap by at least 16,000 bytes, so any stretch of up to 16,000 contiguous bytes lies wholly inside one window: enough for a 4096-bit PEM key (about 3.4 KB with headers), a PGP private key block, and every keyword-and-value rule, whose parts are within a few hundred bytes of each other (including `heroku_api_key =`, a blank line, then the value, which gitleaks misses when the blank line falls just past byte 100,000). Windows start on a line boundary when lines are short, and a window advances at least 34,000 bytes (typically 74,000); a long line is cut mid-line with the same overlap. Cuts always fall on a UTF-8 character boundary, so a multibyte character is never split. The window records how far into its first line it starts, in bytes.

Details that keep windows honest:

1. gitleaks skips a file whose first bytes look binary, so a window that began at a line starting `MZ`, `%PDF`, `%!`, `{\rtf`, `BZh`, `CWS` or `FWS` would be skipped silently. Every window therefore starts with a neutral first line (`# affidavit window`), and original line numbers are the window line plus `startLine - 2`. After writing the windows the host also runs the same signature check over every window (offset signatures such as `ustar` at byte 257 can still match) and reports a hit as a `window-skipped` notification that makes the run `partial`.
2. Rules that match on the file path (`kubernetes-secret-yaml`, `hashicorp-tf-password`, `freemius-secret-key`, `nuget-config-password`) need the real name, so a window is written at `wNNNN/pNNNN/<original path>`. The generated directories are what maps a finding back (any number of digits, any characters after the prefix, including newlines), and the rest of the path is ignored, so a repo file name cannot forge or collide with another window.
3. Names gitleaks reads as archives. Probed on the pinned image on a Linux filesystem with plain text under about 500 names: gitleaks picks an archive format from the file's own name, fails to extract plain text, and drops the file with exit 0, in the snapshot pass and the windows pass alike (directory names do not matter). The rule, which predicts every probed name, is in `ARCHIVE_NAME`: `.gz .zip .tar .bz2 .xz .zst .lz4 .br .sz .7z .rar .zz` anywhere in the name followed by anything (so `a.zip.js`, `config.zip.env`, `a.tar.foo`, `a.zipx`, `a.zstd`, `a.gzx` are dropped), `.lz` and `.mz` only as the last extension, in any case. `.tgz .tbz2 .txz .tzst .jar .war .Z .lzma .cpio .lzip .rpm .deb .cab .iso .bz` and ordinary names are scanned normally. A file with such a name and no archive signature in its content is the `archive-name-mismatch` kind (a coverage loss, so `partial`), and it is windowed whatever its size, under a neutral name: the archive tokens in the name get an underscore (`a.gz.yaml` becomes `a._gz.yaml`), the final extension is kept, so path rules still apply. No path-scoped rule in the vendored config mentions an archive extension (a unit test checks this), so none is lost by the renaming. A file with such a name that really is an archive is the `skipped-file-type` kind as before.
4. Columns, probed on the pinned gitleaks: they are counted in BYTES (a multibyte character before a finding moves it by its byte length), on the first line of a file they are 1-based, and on every later line they come out one higher (gitleaks counts the newline). The first original line of a window is window line 2, which gitleaks reports with the later-line convention, so on that line the remapped column is `column + startColumn - (startLine === 1 ? 1 : 0)`. A docker test compares remapped regions with the snapshot pass for LF, CRLF, minified and multibyte files. The snapshot pass's own columns are unreliable after its first 100 KB chunk (a gitleaks bug); the remapped windows columns do not have that problem. Findings are deduplicated only when rule, file and absolute start and end position all agree.
5. Budget and order. At most 256 MiB of windows are written per run (`maxWindowBytes`), counted as bytes are written, so it is a hard cap: a file that would cross it stops there and is listed in a `windows-budget-exceeded` notification (the run is `partial`). 256 MiB is a safety limit against filling the disk and keeping gitleaks busy for a very long time, since windows duplicate each large text file about 1.2 times; it is not a measured number. Files that already carry a coverage flag (`chunk-split-risk`, `multiline-split-risk`, `archive-name-mismatch`) are windowed first, then the rest smallest first, so a repo cannot steer the budget with its file names. A file that cannot be windowed because writing failed (a name or path too long, a full disk) is reported as `window-skipped` and does not stop the others.
6. Each call uses its own directory, `<copy>.windows-XXXXXX` created with a unique suffix, and removes only that directory in a `finally` block, on success and on failure. Two runs on one copy do not touch each other's windows, and a leftover directory is never deleted.

Findings are mapped back to `/src/<original path>` and the original line. The report has origin `windows` and `windowedFiles` lists the files. A finding can also appear in the snapshot report; merge by rule, path and region. What remains uncovered is a secret longer than 16,000 bytes, which only the private-key rule can match (its body is unbounded); `multiline-split-risk` and `chunk-split-risk` stay as defence in depth for that, and also flag files the windows pass already covers, so `partial` is noisy for large files (a lead question). Docker tests check each case against the real pinned gitleaks: the decoy variants, the whitespace line straddling byte 100,000 with a token across the hard cut, the heroku case, windows that would begin with `MZ` or `%PDF`, a Kubernetes secret in a `.yaml` file whose blank line falls past byte 100,000, every probed archive-like name, the column conventions, and a seeded sweep.

A directory discovery cannot list is an `unreadable` notification. Inspection runs at least one worker, and a failed read stops the others.

Inside a quarantined `.git`, only `index` and `objects/` are skipped (files under `.git/objects/**` are never inspected, including loose files planted in the fan-out directories: git history is an accepted gap) (expected binary); `config`, `info/exclude`, `hooks/*`, `refs/*`, `HEAD` and the rest are text and are checked like any other file. `objects/` may hold only two-hex-digit directories, `pack` and `info`; anything else counts as extra content and makes Semgrep and OSV results partial. Residual gap: a file type the library recognises whose header is entirely plain text and missing from the signature table would be missed. Also inside a quarantined `.git`, the contents of `logs/`, `modules/`, `worktrees/`, `lfs/` and `sequencer/` are not inspected for non-metadata beyond the gitleaks coverage check (submodule, worktree and history data are part of the git-history accepted gap).

### gitleaks rules and license

`config/gitleaks.toml` is the default rule set of gitleaks v8.30.1 vendored as a standalone config (222 rules), extracted from the binary inside the pinned image rather than downloaded, with the upstream global `[allowlist]` block removed. That block skips `node_modules`, lockfiles, vendored directories, images, `.gem` files and several value patterns, all of which a hostile repo can use to hide a secret. Accepted gaps: the 13 rule-level `[[rules.allowlists]]` blocks upstream ships stay as shipped, for example `@octokit/auth-token/README.md` for the GitHub token rules, Yocto `.bb`/`.bbappend`/`.bbclass`/`.inc` lines for `generic-api-key`, and per-rule stopwords and value regexes. Removing the global list raises false positives (placeholders such as `${VAR}` are no longer skipped); arraignment scoring is where those are weighed.

License status, stated plainly: gitleaks is published by its authors under the MIT license, and this file is a modified copy of its default configuration. This repository is public and the file is already in it, but it carries no MIT copyright and permission notice yet, and the pinned image does not bundle the license text. Adding the notice is pending a decision by the lead; until then treat the file as not yet cleared for redistribution beyond this repository. The header comment in the file records the origin and the change.

### What reports contain

Secret values are masked in the gitleaks report (`--redact`), so L1-01 cannot take them from there. It must take secret locations from the SARIF regions (file, start and end line and column) and read the values from the snapshot (or the sidecar, see below) to build its redaction map. Semgrep SARIF is the opposite problem: it carries the raw matched source lines, so downstream redaction (L1-01, L1-07) must be applied to those snippets before anything is stored or shown to an agent.

### Notes for the normalizer (L1-03)

- SARIF artifact URIs are absolute container paths such as `/src/src/app.js`, not repo-relative. Strip the `/src/` prefix. Reports from the quarantine pass are rewritten to the same shape, `/src/<original path>`.
- OSV is run with `--all-packages`, so its report lists packages that have no vulnerabilities. The normalizer must make candidates only from entries with vulnerabilities.
- Semgrep exits 0 even when files failed to parse or timed out. Read `partial` and `notifications` on the run result, not the exit code.

## Running tools

Our configs live in `docker/tools/config/` and are mounted read-only at `/tool-config`.

The tools need a writable `/tmp` (and Semgrep a writable `/root/.semgrep`). With a read-only root filesystem these are supplied as scratch mounts through the port (`scratchDir`), so the port needs no extension. Use a new, empty scratch directory and a new, empty output directory for every tool run of every case. `runTool` creates them and refuses ones that already have content (`ScratchNotFreshError`, `OutputNotFreshError`), so results from another case or run can never be mistaken for this one. After the run it requires the report to be a regular, non-empty file holding valid JSON (a planted symlink is refused, and a truncated report is a failure), or throws `ToolOutputMissingError`. The runner's returned output path is not used (see the runner contract).

A failed run never returns a result: any exit code the manifest does not list throws `ToolFailedError` carrying the exit code and the quarantine list, so a missing or partial report cannot be parsed as findings.

The OSV database mount path is where osv-scanner looks for its cache. In the read-only jail used here (no writable `HOME`) osv-scanner fell back to `/tmp/osv-scalibr`; with `OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY` set it uses `<dir>/osv-scalibr`. If Lane 2's runner sets `HOME`, `XDG_CACHE_HOME`, `TMPDIR` or `OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY` differently, the database must be mounted at the matching `<dir>/osv-scalibr`; a mismatch makes osv-scanner report no offline database and the run fails.

Paths: `buildInvocation` defaults its config directory, and `loadToolManifest` its manifest, to `docker/tools` found by walking up from the source tree. A deployment that does not ship `docker/tools` next to the code must pass `loadToolManifest(path)` and `ToolRunOptions.configDir` explicitly (apps/worker is the place to wire that). `buildInvocation` is not exported from the package: it does not check the snapshot, so `runTool` is the only entry point.

## Runner contract (Lane 2) and known gaps

`runTool` is tested with `LocalDockerToolRunner`-style runners: plain Docker, the mounts it passes, a returned output path fixed at construction. It does not compare that path with the output directory it passed; it reads the report from the `/out` mount and requires a regular, non-empty, valid JSON file there. Any error a runner throws becomes a `ToolFailedError`.

**Known gap: `GvisorToolRunner` (Lane 2) cannot run these tools as they are.** `packages/sandbox/src/gvisor/mounts.ts` reserves `/tmp` and `/scratch` as container paths, so the scratch mount at `/tmp` is rejected for every tool, and the jail sets `HOME` and `TMPDIR` to `/scratch` and runs as uid 65534. That breaks, at least: the writable `/tmp` the tools need, Semgrep's `/root/.semgrep`, the OSV database path, and writing to the `/out` mount as that uid. This needs Lane 2 and the lead; discovery does not edit Lane 2 code. What the tools need from a runner:

- A writable temp directory and home that the runner provides itself, so discovery does not mount `/tmp` or `/root/.semgrep`. Semgrep needs a writable settings directory (`$HOME/.semgrep`).
- The OSV database where osv-scanner looks. OSV-Scanner 2.7.0 has no flag for it. It honors the environment variable `OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY` (checked on the pinned image: the database is then read from `<dir>/osv-scalibr/<ecosystem>/all.zip`), and otherwise falls back to `$TMPDIR/osv-scalibr`. The port cannot set environment variables, so with `TMPDIR=/scratch` the database would have to sit under `/scratch/osv-scalibr`; a runner that can set the variable is simpler. This is a port question for the lead.
- A uid that can write the `/out` mount and read `/src`, `/rules`, `/tool-config` and the database.
- Allowed roots that cover every host path passed: `configDir`, `rulesDir`, `osvDatabaseDir`, the output and scratch directories, and the derived siblings `<copy>.quarantine` (read-only) and `<copy>.windows-*` (read-only), and the `-quarantine` and `-windows` siblings of `outputDir` and `scratchDir`. Paths are normalised before the suffix is appended. Each `runTool` call creates its own `<copy>.windows-XXXXXX` directory (a unique suffix, so the allowed root must cover the copy's parent directory or that prefix) and removes exactly that directory when it finishes, on success or failure; the sidecar `<copy>.quarantine` stays on disk and should be deleted with the copy.
- A timeout must surface as a non-zero exit code (the gVisor runner returns 124 or 137 after its 10 minute limit); `runTool` fails closed on any exit code the manifest does not list.

Open questions for the lead: what `ToolRunnerPort.run` should return as `outputPath`, since both runners ignore the mount path; and stderr is not returned, so tool diagnostics (OSV extraction errors, gitleaks skipping an archive) are lost. `runTool` compensates with its own checks, but returning stderr or a log path would be better.

## Accepted gaps

- Sidecar files are scanned under neutral names (`q0001`), so gitleaks rules or allowlists that match on path see the neutral name, not the real one.
- Git history (packed objects) is not secret-scanned; `.git` is moved aside and its objects are skipped rather than listed per file.
- gitleaks rule-level allowlists, described above, remain.
- `--x-ignore-semgrepignore-files` is an internal, experimental Semgrep flag and may disappear on upgrade. The flag-pin test and the hostile docker test fail loudly if it does.
- Expect a high `partial` rate on real repos: every archive and other skipped file type is a coverage loss, and OSV-Scanner skips lockfiles under committed `node_modules`. Whether that is the right signal, or whether some should be informational, is a question for the lead.
- An unvendored ecosystem database makes OSV-Scanner fail (exit 127): the offline database must hold every ecosystem the snapshot uses, or the run is a `ToolFailedError`, not a partial result. A repo whose only OSV-readable file is something like `deps.json` or `bom.json` that OSV cannot parse also exits 128 and, because the name is on discovery's lockfile list, fails rather than being partial. Whether such cases should be partial instead is a question for the lead.
- gitleaks matches the `-----BEGIN ... PRIVATE KEY` header case-insensitively using Unicode case folding, so a header written with the Kelvin sign (U+212A) in `KEY` is matched by gitleaks and not by discovery's plain case-insensitive match. That is a gap in discovery's key check unrelated to chunk cuts, and it is covered by the windows pass, not by the flag.
- OSV-Scanner can drop one bad entry inside an otherwise parseable lockfile. It reports that only on stderr, which the port does not return, so it cannot be detected here; returning stderr from the port would fix it.
- Special files (FIFOs, sockets, devices) in the snapshot are not handled by discovery; ingestion must drop them from the scan copy.
- `QuarantinedSnapshot` is nominal at the type level only; JavaScript callers can forge it. `runTool` re-checks that the snapshot is clean before every run.

## Snapshot contract for ingestion (L1-01)

Some repo-controlled files change what a scanner does, and a few have no off switch: gitleaks reads a repo `.gitleaksignore` even with our flags (the docker tests demonstrate this). A hostile repo can also plant `.git/config` to run commands through git. So:

1. Ingestion makes a private copy of the repo for scanning and never scans the original checkout. Files the jailed tools cannot read (mode 000) are invisible to them, so ingestion should fix modes on the copy or record such files as unscanned.
2. It calls `quarantineSnapshot(copyDir)` from `packages/discovery/src/tools`. This moves, at any depth, entries matched by exact name, case-insensitively: `.git`, `.gitignore`, `.gitattributes`, `.gitmodules`, `.gitleaksignore`, `.gitleaks.toml`, `.gitleaksbaseline`, `gitleaks.toml`, `osv-scanner.toml`, `.osv-scanner.toml` and `.semgrepignore`. Only `.git` is moved when it is a directory; a directory that merely has a control name (such as `src/.gitignore/`) stays in place and is scanned, because the scanners act only on files and symlinks with those names. There are no prefix matches, so application code in `.semgrep-lib/` stays and is scanned; `.github`, `.semgrep.yml` and `.semgrep/` stay too (Semgrep never reads them from the target). It is two-phase: everything is found before anything moves, and it refuses to start if the sidecar directory already exists.
3. Nothing is deleted. Moved entries go to a sibling sidecar directory, `<copyDir>.quarantine`, under neutral names (`q0001`, `q0002`, ...). `QuarantinedSnapshot` carries `dir`, `sidecarDir`, `mapping` (neutral name to original path) and `removed` (original paths). Record `removed` as a signal on the case: a repo that plants these files is suspicious. A `QuarantinedSnapshot` can only be created by `quarantineSnapshot`; `runTool` takes it instead of a path and returns the list as `quarantined` on its result.
4. `runTool` makes gitleaks scan the sidecar too, so a secret in a moved file (a `.gitignore` or `osv-scanner.toml` can hold one) is not missed. That second report goes to `<outputDir>-quarantine` with paths mapped back to the originals, and both appear in `reports`. The sidecar still holds the repo's own ignore lists, git metadata and configs: keep it out of any workspace that leaves ingestion, and delete it with the snapshot.
5. `resolveQuarantinedUri(snapshot, uri)` maps a report URI such as `/src/.gitignore` back to the file in the sidecar, so L1-01 can read a quarantined file (for example to build its redaction map). `gitDirExtraContent(snapshot)` lists non-metadata content in a quarantined `.git`: unknown top-level names, unexpected names inside `hooks/` (anything but `*.sample` and git's hook names) and `info/`, and oversized files under `refs/`. `runTool` marks Semgrep and OSV results partial for them, and checks the non-bookkeeping files of a `.git` directory for gitleaks coverage notifications.
6. `runTool(runner, manifest, name, options)` is the only supported way to run a tool. It throws `SnapshotNotCleanError` if any control path is still present, `ScratchNotFreshError` or `OutputNotFreshError` for reused directories, `ToolOutputMissingError` for a missing, empty or non-regular report, and `ToolFailedError` for a failing run.
7. For `BundleManifest.toolVersions`, call `toolVersions(manifest, namesOfToolsThatRan)`. Values are `<version>@<image digest>`. The tool set that ran is known only to the worker (apps/worker), so it must pass it.
8. Names that are not valid UTF-8 follow one policy everywhere: quarantine and every host walk throw `NonUtf8NameError` (and quarantine moves nothing), so ingestion should reject or rename such files.
9. Symlinks inside the copy are not followed by quarantine, but the scanners may see them. Ingestion should drop or flatten symlinks that point outside the copy.

Inline `nosemgrep` and `gitleaks:allow` comments live in source files, so they are handled by flags, not removal.

## Smoke tests

Unit tests run in plain `pnpm test`. The Docker tests run each image offline against `fixtures/corpus/tool-smoke/`: a benign repo, and a hostile one with planted ignore files, configs and rule files, inline suppressions, a git fsmonitor canary, a file over 1 MB, an unparsable file, secrets under `node_modules`, `vendor` and inside a gzip, a secret in a quarantined `.gitignore`, a malformed lockfile, and a Go module (to prove no Go toolchain runs). They are skipped unless explicitly enabled:

```
AFFIDAVIT_DOCKER_TESTS=1 pnpm --filter @affidavit/discovery test:docker
```

PowerShell: `$env:AFFIDAVIT_DOCKER_TESTS = '1'`, then the same command. The first run pulls the three images.

The jail flags in the test mirror `buildDockerRunArgs` in `packages/testing`, which discovery cannot import. A test pins the exact ordered flag sequence against that file, so drift is caught rather than silent. Fixture files that would be live control files or `.json` data are stored renamed (`dot-` prefix, `.fixture` suffix) and restored in a temp copy.

## Updating a pin

Resolve the new tag with `docker buildx imagetools inspect`, run the image to confirm its version, then update `tools.json` (version, tag, digest, reference, resolvedOn) and re-run both test suites. Keep the CI OSV-Scanner digest in step.
