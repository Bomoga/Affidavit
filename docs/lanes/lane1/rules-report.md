# Own Semgrep rules: corpus regression report (L1-04)

Everything below comes from real runs. Anything not run is `[metric]`. The rules are written from scratch; no registry rule or rule text is used, and Semgrep is only ever given our own rules directory (`--config /rules`).

## Rules

All files are in `packages/discovery/rules/semgrep/`, one rule per file, each with a Semgrep test file of the same base name in `packages/discovery/rules/tests/`. The two IDOR files are generated by `packages/discovery/rules/generate-idor-rules.mjs` (edit the generator, not the YAML).

| Rule id                                      | Class     | Kind             | What it flags                                                                                                                                                                                                                                                                                      |
| -------------------------------------------- | --------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `affidavit.injection.sql-concat`             | injection | pattern          | SQL text built by template interpolation or any concatenation, as the first argument or in a `{ sql: ... }` or `{ text: ... }` option object, of `query`, `execute`, `raw`, `whereRaw`, `orderByRaw`, `havingRaw`, `joinRaw` and similar, also as a bare call                                      |
| `affidavit.injection.sql-request-taint`      | injection | taint, one file  | `req.body`, `req.query`, `req.params`, headers or cookies reaching the first argument of those calls, directly or through variables, without a numeric coercion                                                                                                                                    |
| `affidavit.injection.nosql-where-template`   | injection | pattern          | MongoDB `$where` (object key or mongoose `.$where(...)`), also built into a variable first, from a template or concatenation with a value that is not numeric (numeric coercions and literals are excluded)                                                                                        |
| `affidavit.injection.nosql-operator-request` | injection | taint, one file  | a request value (`req.body` or `req.query`; not `req.params`, which is always a string in Express) reaching a MongoDB filter, an update or replacement document (`updateOne`, `updateMany`, `replaceOne`, ...), `aggregate`, `findById` or `distinct` (operator injection such as `{"$ne": null}`) |
| `affidavit.idor.route-param-to-data-access`  | idor      | pattern, ordered | `req.params` (or Koa `ctx.params`) read into a `const`, `let` or `var`, or used inline, and passed to a data-access call with no ownership check on the path to that call                                                                                                                          |
| `affidavit.idor.request-id-to-data-access`   | idor      | pattern, ordered | the same for an id-like field (`id`, `_id`, `*Id`, `*ID`, `*_id`) from `req.body` or `req.query`. Broader than the task text, needed for the benefits label                                                                                                                                        |

Data-access receivers for the IDOR rules: names ending in dao, repository, repo, store, model or collection (with any dotted prefix such as `this.orderRepo`), capitalised model classes except well-known globals (`Joi`, `Math`, `JSON` and so on), `prisma`, `db`, `knex` and `sequelize` chains (`prisma.order.findUnique`), and `db.collection(...)` or `knex(...)`. The method must read or change data (`find*`, `get*`, `update*`, `delete*` and similar), so `Joi.string().validate(id)` is not data access.

An ownership check is an `if` that compares the identifier with an id-like field of the signed-in user (`id`, `_id`, `userId`, `user_id`, `uid`, `sub` on `req.session`, `req.user`, `req.auth`, `req.session.user` or `ctx.state.user`; `req.session.csrfToken` does not count) and either wraps the call in its then-branch (an else-branch does not count), or comes before the call and its body returns, throws or calls `ctx.throw(...)`, braced or not. A bare `next(err)` without `return` does not stop the handler, so it does not count; `return next(err)` does. A guard whose body only logs, and a check placed after the call, do not count (all tested). Each data call is judged on its own, so a guarded call does not clear another call on the same identifier.

Where an IDOR finding goes: when the identifier is read into a variable, on the request expression of that read (`req.params`, `req.body`), so it lines up with how the corpus labels IDOR sources; on the call when the identifier is used inline. One read can give several findings at that spot (one per unguarded call); the regression counts them per rule. The wrapper's SARIF carries no data-flow trace, and a taint rule would report on the sink call instead.

Known misses of the IDOR rules (not detected, so not reported): Next.js app-router handlers that receive `{ params }` as an argument, a params object copied under another name (`const p = req.params; p.id`), a call whose receiver does not look like data access (a plain helper function, `this.save(...)`), and guards written another way (a `switch`, a ternary, a helper such as `assertOwner(id)`, an `else`-branch that returns). The request-id rule only looks at names ending in `id`, `Id`, `ID` or `_id`, so a field such as `owner` is not seen.

Known limits, by design: every rule sees one file at a time (NodeGoat's gate issue crosses a file boundary, so it is caught by the pattern rule at the sink, not by taint); an ownership check in middleware, a role check, or a check in the data layer is not seen.

Known false positives:

- `nosql-where-template` and `sql-concat` flag a template whose interpolated value is a non-literal constant (the corpus negative control is such a case, and the corpus expects the flag). `sql-concat` also flags a constant table or column name interpolated from a variable, and a value validated elsewhere. Semgrep's constant propagation does exclude a variable that is a string literal.
- The IDOR rules flag a call that is already scoped to the owner some other way, for example `findOne({ _id: id, owner: req.session.userId })`, and an identifier checked in a helper or in middleware.
- `sql-concat` does not follow variables (the taint rule does), so a statement built into a variable and then queried is only caught by `sql-request-taint`.

## How a run is made

- Image: `docker.io/semgrep/semgrep@sha256:cc1b68266f267878b39739373ea9985b9a78e5d64497dd875c8de100b22695ed` (Semgrep 1.184.0, from `docker/tools/tools.json`).
- Command: `AFFIDAVIT_DOCKER_TESTS=1 AFFIDAVIT_RULES_STAMP=write pnpm --filter @affidavit/discovery exec vitest run corpus-regression.docker` (PowerShell: set the two variables with `$env:` first). It needs Docker and network access to github.com.
- The test (1) runs `semgrep --test` over the rule files and their test files, (2) fetches NodeGoat at the pinned commit with the corpus fetch script (commit, tree and archive hash verified), plus the safe variant and the negative control (corpus patches applied), (3) copies each tree without its `.git`, quarantines it, and runs the rules through `runTool` (the merged wrapper: no network, read-only source, hardened flags), (4) compares the per-rule results with the corpus labels and `packages/discovery/rules/corpus-expectations.json`, and fails on any difference it cannot explain.
- Every rule change runs it: `regression-stamp.json` holds a digest of the inputs (rules, rule tests, the generator, expectations, the Semgrep entry of `tools.json`, the NodeGoat pin, patches and labels, the harness files, the corpus fetch script, and the wrapper files `invocations.ts`, `run.ts`, `quarantine.ts`, `manifest.ts`, `walk.ts`, `index.ts` that build and run the Semgrep command line). The always-on unit test `corpus-regression.test.ts` fails when that digest no longer matches, and also checks that the stamp names the pinned image and the pinned NodeGoat commit. The stamp also records a digest of the normalised run output (all findings and the per-rule table, not notifications). The stamp is written by the test itself, so it shows a run happened but cannot prove it; CI running the Docker test is a question for the Lead.
- Matching: a finding is counted against a labeled issue when it is in the label's file and its lines overlap the label's `range`, or the label's `source` range in the source file.

### Semgrep notifications (partial runs)

Every run on every tree reported notifications in vendored third-party files under `app/assets/vendor/` only: a parse error in `chart/morris-0.4.3.min.js` and timeouts of the heavier rules on `jquery.min.js`. The wrapper marks such a run `partial`. The rules were deliberately not given a path exclusion for vendored or minified files, because a repo could hide code in a directory with such a name. The regression tolerates only exact (file, rule) pairs listed in the expectations: the parse error on `chart/morris-0.4.3.min.js`, and a timeout of any of the six rules on `chart/morris-0.4.3.min.js`, `chart/raphael-min.js` or `jquery.min.js` (19 pairs). It rejects any path containing `..`. After repeated flakiness the list covers every rule on those three files, not only the pairs I saw: I saw timeouts of the two IDOR rules, `nosql-operator-request`, `sql-request-taint` and `sql-concat`, and I did not see every pair, so some tolerated pairs are guesses. Any other file or notification fails the test. The timeouts depend on machine speed.
