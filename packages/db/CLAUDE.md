# @affidavit/db

**Owner:** Lane 1 (Intake and Platform)

**Mission:** Drizzle schema and migrations, row-level security, the Graphile Worker stage queue, and the real `CaseStore` and `EventSink` (`PgCaseStore`, `PgEventSink`).

## Commands

Run from this directory, or add `--filter @affidavit/db` from the repo root.

- `pnpm typecheck`, `pnpm lint`, `pnpm test` (pure unit tests only)
- `pnpm test:pg` runs the Postgres suites. It needs `AFFIDAVIT_TEST_DATABASE_URL`, the superuser URL of a throwaway server (for example compose Postgres). Each suite creates and drops its own database. Without the variable the suites skip with an explicit message. CI does not run them until a Postgres service is added.
- `pnpm db:generate` after editing `src/schema.ts`. Security objects (roles, RLS, grants, triggers) live in the hand-written `drizzle/0001_security.sql`; add later ones with `pnpm db:generate --custom --name=<name>`.

## Invariants

- Every table has `tenant_id`; RLS is enabled and forced on all of them; every foreign key includes `tenant_id`.
- Role model. `bootstrapRoles` runs once as a superuser (PG16 only lets a superuser set NOSUPERUSER/NOBYPASSRLS, role-level settings or a database owner): it creates `affidavit_owner` (non-superuser database owner), `affidavit_app` and `affidavit_worker`, pins the login roles' `search_path`, and makes the owner the database owner. `applyMigrations` then runs as `affidavit_owner`; the migration only verifies the login roles' flags. The owner owns every object, including the SECURITY DEFINER functions, and is subject to FORCE RLS (explicit `owner_access` and `owner_read` policies on `tenants`, `stage_jobs`, `stage_runs`, `cases`, `stages`). Passwords are set at provisioning (`setRolePassword`, SCRAM verifier), never in a migration or a committed file. The two login roles are plain (no BYPASSRLS, no memberships, no TEMP, nothing owned): `affidavit_app` (tenant tables under RLS, plus `enqueue_stage()`) and `affidavit_worker` (queue schema and `claim_stage_run()`, no tenant tables). Open pools only with `openPool(url, role)`, which refuses a superuser, any membership, REPLICATION, role-level settings other than `search_path`, owned objects, the wrong role, or a wrong `search_path`.
- Tenants are created by the owner (`provisionTenant`), not the app role.
- Tenant is set per transaction (`withTenant`, `set_config(..., true)`), and the connection is `DISCARD ALL`ed before it returns to the pool. No tenant set means no rows. RLS defends against query-building bugs; code with arbitrary SQL as the app role could still call `set_config`.
- Known limits, for Adrian: the worker role can DELETE and UPDATE Graphile job rows (Graphile needs it), so failed-job records are not tamper-proof; the worker process also holds the app pool, so a compromised worker can act as any tenant through it; `exhibits.result` and verdict writes go through the app role. None of these is closed by this package. Port writes are not lease-fenced: `PgCaseStore` and `PgEventSink` write in their own transactions and do not check the lease, so a zombie handler that ignores `ctx.signal` can still write through them (a question for the lead; a fence would need the lease token on every port call). Also: Postgres denies the app role `ALTER ROLE ... SET app.tenant_id` (tested). It does NOT stop the app role changing its own `search_path` default (PostgreSQL lets an ordinary role do that; tested as documented behaviour): the change fails closed at the next `openPool`, not before; and `provisionTenant` needs the owner credential in whatever process calls it (a follow-up could add a SECURITY DEFINER `provision_tenant` for a narrow role; not built).
- READ THIS BEFORE WRITING THE ORCHESTRATOR (L1-10). (1) Abandon attempt N (`failStageRun`, which needs an expired lease) BEFORE enqueueing N + 1: `claim_stage_run` refuses a second open attempt of the same visit, so N + 1 would fail at claim otherwise. (2) A handler must check `ctx.signal.aborted` before every write it makes through a port (`PgCaseStore`, `PgEventSink`); those writes are not fenced by the lease. (3) `listFailedStageJobs` and `stageJobState` treat a job with its attempt used up and no lock as failed even with no error (graphile-worker 0.18 clears the lock of jobs locked for over 4 hours without recording one), unless its attempt completed or holds a live lease (then it is a long-running handler, `running`).
- Handler ordering: make the last writes (including the case transition through `PgCaseStore`) first and call `ctx.complete(tx)` last. `resumeDecision` returns `completed-not-advanced` for a completed attempt whose case is still at that visit of a non-terminal stage, so a handler that completes without advancing is not mistaken for a finished stage. `pg_advisory_xact_lock(stage_lock_key(tenant, case, stage))` serialises `enqueue_stage` and `claim_stage_run` (one shared SQL helper; `stage_job_key` is the shared job key, equal to `stageJobKey` in TS). Adoption (`completeStageRun` without a token) is refused in SQL unless the case has left the visit.
- `openPool` returns a branded `CheckedPool`; the stores, the sink and the queue functions only accept `AppPool` or `WorkerPool`. Heartbeat failures abort `ctx.signal` once the last confirmed lease expiry has passed or after three failures in a row. `src/kill-child.ts` is a test helper (a worker in its own process, run through tsx, given an allowlisted environment (`childEnv` in `test-support.ts`: what node needs plus the CHILD_* settings, so not the superuser URL or anything else of the parent's) and only the app and worker URLs) used by `kill.pg.test.ts`; it is not part of the package API and is never emitted (the build is noEmit).
- The app role cannot touch the Graphile Worker tables. It enqueues only through `enqueue_stage()` (SECURITY DEFINER; tenant forced from the transaction setting; checks the case exists; writes a durable `stage_jobs` record; returns false when the key is already queued, running or failed). The worker role claims through `claim_stage_run()`, which refuses a payload with no matching `stage_jobs` record, so a forged or rewritten job fails at claim and shows in `listFailedStageJobs`. An attempt starts at most once (`stage_runs`, with a lease). Handlers get a `StageContext`: complete the attempt in the handler's own final transaction (`ctx.complete(tx)`). Handler errors set `failed_at` and `error`. Leases are enforced in SQL, against the wall clock (`clock_timestamp()`, not `now()`, so a transaction that began before the expiry cannot act as if it still held the lease; `stage_run_heartbeat`, `stage_run_complete`, `stage_run_fail` and the `stage_runs_guard` trigger all use it, and have a 5 second `lock_timeout`): the app role has no UPDATE on `stage_runs` and cannot read `lease_token`. `claim_stage_run` hands the claimer a secret token; heartbeat and holder completion (`stage_run_heartbeat`, `stage_run_complete`, which run in the caller's transaction) need that token and a live lease; the orchestrator can abandon (`failStageRun`) or adopt (`completeStageRun`) only an EXPIRED lease; a lease is capped at an hour (claim) and the database refuses to extend an expired one. The task wrapper heartbeats every lease/3 (one heartbeat in flight at a time: a hung database does not collect a queue of them) and aborts `ctx.signal` when it cannot, with a timer set to the last confirmed expiry. A holder whose process was paused (no timer ran) is still refused: the lease guard (`GuardedCaseStore`, `GuardedEventSink`, `ctx.checkpoint`) compares the clock with that deadline (`leaseLost(signal)`) before every port write. Writes through other ports (`PgCaseStore` opens its own transactions) are not atomic with `ctx.complete(tx)`; a kill between them leaves the attempt open and the orchestrator adopts it once the case has left the stage. `enqueue_stage` requires the case to be at that stage now, records the stage visit (stage-history ordinal, written by a trigger on `cases`; the app role cannot insert history), and refuses to reuse an attempt number for a later visit. `claim_stage_run` refuses a job whose case left the stage or visit, a superseded attempt, or a second open attempt of the visit; the refusal fails the Graphile job. A killed worker leaves an open attempt (or, if it died before claiming, a stale-locked Graphile job with no error). The orchestrator (L1-10) calls `resumeDecision({ appPool, workerPool }, p, { staleLockSeconds })`, which also reads the queue job state: an open attempt whose lease expired is `next-attempt` only when its job is stale, failed or gone, or the lease expired more than `staleLockSeconds` ago (otherwise `wait`: the holder may be winding down); `next-attempt` means abandon if open, charge budget, `enqueueStage` with attempt + 1 (attempt numbers must be unique per case and stage across visits); `adopt-complete` means the case left the visit and the lease is gone. Graphile retries are off (`max_attempts` 1): resume is explicit, and `listFailedStageJobs` surfaces failed and stale-locked jobs.
- Append-only (triggers stop the application roles; the owner could still disable them): verdicts, events, ballots, stages, cost_rows, escalations, stage_jobs. Write-once: `exhibits.result`, `stage_runs.completed_at` and `failed_at`. Inserts are guarded too (cases start at intake with zero counters, exhibits and stage runs start without a result). `cases` identity, file, score and floor are immutable; stage changes are also checked in SQL (table, F3, appeals). An event's seq must be below the case counter (call `nextSeq` first); ballots and escalations need their event row; `cost_rows` amounts are non-negative. JSON blobs must agree with their columns (`*_blob_matches`, plus `cases_repo_matches` for the repo column, `escalations_detail_matches` for the detail, `events_verdict_case_matches` for the verdict inside a `verdict-written` event); a test removes each key in turn from every blob. Verdict insertion does not check the case stage (parity with `FakeCaseStore`; a question for Adrian).
- Migrations must run as the designated owner role: the `owner_access` policies on `tenants`, `stage_jobs` and `stage_runs` name the role that ran them. After a Graphile Worker upgrade, re-run `applyMigrations` to grant and add policies for new queue tables.
- Budget arithmetic: `remaining_usd` is exact `numeric` rounded half away from zero at 6 decimals; `FakeCaseStore` rounds a float with `Math.round`. They can differ by one micro-dollar on exact half-micro values.
- `AFFIDAVIT_TEST_DATABASE_URL` must never point at a shared server: the tests create and alter cluster-wide roles (`affidavit_app`, `affidavit_worker`) and temporary roles. Use a throwaway container.
- Every function pins `search_path`; raw SQL names `public.<table>` (Drizzle cannot qualify `public`).
- Store rules match `FakeCaseStore` in `packages/testing`: `rejectTransition` plus a row lock in `transition`. Add a case to `src/transition-cases.ts` for any rule change.
- Queue jobs are keyed on tenant, case, stage and attempt.
- Add a new tenant table: schema, migration with FORCE RLS, policy and grants, and a line in the isolation test.
- Orchestration (L1-10, `orchestration.ts`, `stage-attempts.ts`). `apps/worker` only wires config and stage work into these.
  - `stageHandler(core, ...)` runs stage work in the required order: work and case transition, `ensureStageJob` for the stage the case is now at, `ctx.complete(tx)` last. Ports passed to a core are lease-guarded (`GuardedCaseStore`, `GuardedEventSink` refuse writes once `ctx.signal` aborted). A core that returns without moving the case fails with `StageDidNotAdvanceError` (it becomes `next-attempt`).
  - Events: `recordOnce` skips an event of the same type, stage and payload that is already stored FOR THE CURRENT VISIT: `env.events` returns only events at or after the visit's entry seq (`stages.entry_seq`, the case's event counter when the stage was entered, written by the trigger on `cases`; 0 on older rows means every event). Cores emit events with it BEFORE the transition and make the transition their last write, so a retry repeats nothing and a kill after the transition has nothing left to emit; a revisit of a stage emits its events again. Events a core emits for the NEXT stage (before its transition) belong to the visit being left.
  - Attempt numbers: `stageAttemptState` returns the latest attempt of the CURRENT visit, how many attempts the current visit has (`visitAttempts`, what `maxStageAttempts` counts) and the next unused number across all visits (`enqueue_stage` refuses a number used for an earlier visit). Never hardcode attempt 1 for a stage that can be revisited.
  - `reconcileOnce` = (1) `listFailedStageJobs` then `resumeDecision` (abandon, charge a zero-amount row, enqueue the next unused attempt; or adopt), (2) a sweep (`list_open_cases()`, worker role only, SECURITY DEFINER, ids and stage only) of the open cases whose latest attempt of the current visit is NOT live (no job, failed, completed without advancing, expired lease, dead job), so a case whose current stage has no job gets one (handler failed or was killed after its transition, a case opened but never enqueued) and a completed-but-not-advanced attempt is retried. Healthy queued or running cases are not listed. `listFailedStageJobs` leaves out failures recovery has nothing left to do for (`stage_attempt_handled`: superseded by a later attempt of its visit, flagged for that visit, or the case left the visit with no open run; `includeHandled` shows them; a job with no `stage_jobs` record, such as a forged one, is never handled). Both scans are bounded (`sweepLimit`, at most 500 failed jobs and 1000 cases) and keyset paged: a short page starts over, a full page continues after its last row next pass (cursors kept per worker pool, or pass `cursors`). Recovery is safe from several workers: the retry (re-read state, abandon, charge, enqueue) runs under a per case and stage advisory lock (a key space of its own) and re-reads the state under it, so concurrent reconcilers produce one attempt and one cost row. A retry is superseded unless the failed attempt is the latest of the visit.
  - `review_flags` (insert-only, one row per tenant, case, stage and attempt; the app role has exactly SELECT and INSERT): written when the attempts of the CURRENT visit reach `maxStageAttempts` or the budget is exhausted, and stores that visit. It blocks retries and the sweep for its own visit only, so an appeal that returns to the stage starts afresh (visit 0 is a row from before visits were stored and matches every visit). The case stays where it is and is never dismissed. The retry charge is a zero-amount cost row; whether it should reserve a stage budget is a question for the lead. The escalation shape is CR-8 in `docs/lanes/lane1/contract-requests.md`; nothing reads the flags yet.
  - `PgCaseFileSource` is the keyed `CaseFileSource`. The task wrapper refuses a queue job whose Graphile key does not equal the key of its payload.
  - Sweep limit: `sweepLimit` (default 500) cases per pass in (tenant, case id) order, continuing after the last one on the next pass.
  - `startCase` is not atomic by design; the sweep repairs a crash after `open`.
